# Skyra LogHub — Canonical JSONL Storage Contract
**Version:** 1.0.0  
**Status:** Approved Specification  
**Architecture Reference:** ADR-011 (File-First Analytical Architecture), ADR-002 (Canonical JSONL Log Event Contract)

---

## 1. Scope & Objective

This contract governs the local file system layout, naming conventions, rollover criteria, concurrency safety, access control, retention, and transport-readiness for JSONL log files generated by Skyra Logging SDKs (`logger-node`, `logger-python`, etc.) and ingested by Skyra LogHub workers.

This document establishes the storage interface without implementing the full physical writer runtime (deferred to subsequent tasks).

---

## 2. Directory Hierarchy & Partitioning

To ensure strict multi-tenancy, cross-service isolation, and high-throughput concurrent writing without locks across projects or processes, all log files must adhere to the following deterministic directory path hierarchy:

```text
${LOG_ROOT}/
  └── ${PROJECT_ID}/
      └── ${ENVIRONMENT}/
          └── ${SERVICE_NAME}/
              └── ${INSTANCE_ID}/
                  └── ${YYYY-MM-DD}.part-${PART_INDEX}.jsonl
```

### Path Components & Validation Constraints

| Component | Description | Constraint / Pattern | Example |
| :--- | :--- | :--- | :--- |
| `LOG_ROOT` | Base path configured via `SKYRA_LOG_ROOT` (defaults to `/var/log/skyra` on Linux or `.logs` in local development). | Absolute valid path, existing or auto-created. | `/var/log/skyra` |
| `PROJECT_ID` | Canonical enterprise project code (kebab-case). | `^[a-z0-9]+(-[a-z0-9]+)*$` (Max 64 chars) | `skyra-business-suite` |
| `ENVIRONMENT` | Target deployment tier (lowercase). | `production` \| `staging` \| `development` \| `test` \| `local` | `production` |
| `SERVICE_NAME` | Subsystem or microservice identifier (kebab-case). | `^[a-z0-9]+(-[a-z0-9]+)*$` (Max 64 chars) | `api-gateway` |
| `INSTANCE_ID` | Process, container, pod, or worker instance ID. | Hostname, pod name, or UUIDv4 (Max 128 chars). | `pod-auth-7bf9b8c65-x9z2l` |
| `YYYY-MM-DD` | UTC calendar date of event recording. | Strict ISO 8601 UTC date: `^\d{4}-\d{2}-\d{2}$` | `2026-10-21` |
| `PART_INDEX` | Monotonically increasing zero-padded 4-digit segment index. | `^\d{4}$` (Starts at `0000`) | `0000`, `0001` |

## 3. File Format & Content Rules

1. **Format:** JSON Lines (`.jsonl`), MIME type `application/x-ndjson`.
2. **Encoding:** Strict UTF-8 without Byte Order Mark (BOM).
3. **Delimiter:** Single Unix newline `\n` (`0x0A`). Carriage returns `\r` (`0x0D`) are prohibited.
4. **Line Invariant:** Exactly one valid JSON object per line conforming to `log-event.schema.json` v1.
5. **Atomic Lines:** Writers must append complete records followed by `\n`. Partial lines or multi-line JSON structures (such as unescaped newlines in stack traces) violate the contract and must be rejected.
6. **No Trailing Garbage:** Files must terminate with `\n` after the last record.
7. **No Duplicate Keys:** Every JSON record must have strictly unique property names within each object scope.

---

## 4. File Lifecycle & Rollover Rules

Log writers must adhere to both UTC calendar day rollover and size-based rollover:

### 4.1 UTC Calendar Day Rollover
- At midnight UTC (`00:00:00.000Z`), writers must immediately finalize the current active file and open a new segment under the new UTC date: `${YYYY-MM-DD}.part-0000.jsonl`.
- The timestamp of the log event (`@timestamp`) dictates the target calendar partition. Under normal operation, events are flushed in real time to the current UTC date.

### 4.2 Size-Based Rollover
- **Default Maximum File Size:** 100 MiB (104,857,600 bytes). Configurable between 10 MiB and 250 MiB via `SKYRA_LOG_MAX_FILE_SIZE_MB`.
- When an active file reaches or exceeds the threshold, the writer closes the file and increments the part index:
  ```text
  2026-10-21.part-0000.jsonl (100 MB -> Closed)
  2026-10-21.part-0001.jsonl (Active)
  ```
- Part numbers are formatted as `%04d` (e.g., `0000`, `0001`, ..., `9999`).

### 4.3 Inactivity Rollover (Optional)
- In low-throughput microservices, if an active file remains open across an extended maintenance window, the file remains active until the next UTC day transition or until explicit shutdown flush.

## 5. Concurrency & Multi-Process Safety

1. **Mandatory Single-Writer Instance Isolation:**
   - **Strict Rule:** Exactly one logical writer process per physical log file segment. Multi-process or multi-thread concurrent writing to the same physical `.jsonl` file is strictly prohibited.
   - Every application process, container, pod, PM2 worker, or execution thread must write exclusively to its own dedicated `${INSTANCE_ID}` directory (`${LOG_ROOT}/${PROJECT_ID}/${ENVIRONMENT}/${SERVICE_NAME}/${INSTANCE_ID}/`).
   - Writer processes never share file descriptors or compete for file locks.
2. **`O_APPEND` Atomicity Caveat & Boundaries:**
   - Files are opened in append mode (`a` / `O_APPEND`).
   - **Critical Architecture Boundary:** Writers and ingestors must NOT rely on OS `O_APPEND` or `PIPE_BUF` (4096 bytes) for concurrency safety. Structured JSON log events containing stack traces, HTTP payloads, or database metadata frequently exceed 4 KiB. Furthermore, Windows NTFS, NFS, and SMB network mounts do not provide atomic interleaving guarantees. Single-writer instance isolation is the sole authoritative mechanism ensuring record integrity.
3. **Flushing, Buffering & Durability:**
   - Writers should employ an in-memory buffer (e.g., 64 KiB or 250 ms maximum latency) to maximize I/O throughput.
   - Synchronous `fsync` is triggered on `fatal` and `error` events to guarantee crash durability.
   - Process shutdown hooks (`SIGTERM`, `SIGINT`, `beforeExit`) must flush in-memory buffers before process termination.
4. **Partial-Line Recovery & Corruption Handling:**
   - If an abrupt power loss or SIGKILL produces an incomplete trailing byte sequence (lacking a terminal `\n` or terminating in partial JSON):
     - Ingestors and compactor workers scan from byte 0 and parse records line-by-line.
     - The corrupted or truncated trailing fragment is cleanly quarantined into an ingestion recovery log (`${YYYY-MM-DD}.corrupt.log`) with offset recording.
     - All prior complete lines terminating with `\n` are parsed and committed without data loss.

## 6. Retention, Compression & Cleanup

1. **Local Retention Tier:**
   - Active raw JSONL files remain uncompressed for immediate reading by the Compactor/Sync agent.
   - Files older than `SKYRA_LOG_LOCAL_RETENTION_HOURS` (default: 48 hours) or already compacted into Parquet are eligible for archival or deletion by background retention workers.
2. **Compacted Parquet Archive:**
   - The LogHub Compactor converts finalized daily JSONL files into columnar snappy/zstd compressed Parquet tables partitioned as:
     `parquet/${PROJECT_ID}/${ENVIRONMENT}/${YYYY}/${MM}/${DD}/${SERVICE_NAME}.parquet`.
3. **Zero Data Loss on Compaction:**
   - An active `.part-XXXX.jsonl` file is never deleted until verified as fully compacted into Parquet and validated against the checksum manifest.

---

## 7. Security, Permissions & Sanitization

1. **File System Permissions:**
   - Directories: `0750` (`rwxr-x---`) owned by the application service account.
   - Files: `0640` (`rw-r-----`) readable only by the application process and the Skyra LogHub collector/compactor group.
2. **Pre-Write Sanitization Requirement:**
   - Prior to serialization into JSONL, every event must pass through the redaction pipeline.
   - Sensitive tokens (passwords, JWTs, bearer tokens, credit cards, SSNs, API secrets) must be redacted to `[REDACTED]`.
   - Stack traces and database queries must be sanitized to eliminate raw literal values.

---

## 8. Failure Handling & Circuit Breaking

When local disk writes fail (e.g., disk full `ENOSPC`, permission denied `EACCES`, read-only filesystem `EROFS`):
1. **Fallback Destination:** The SDK attempts an immediate fallback to a secondary buffer directory (e.g., `/tmp/skyra-fallback/` or `process.env.TEMP`).
2. **Circuit Breaking:** If all file targets fail, the writer must drop non-critical (`trace`, `debug`) logs and log a single rate-limited diagnostic to `stderr`. Under no circumstances may a logging failure crash the host application.
3. **Internal Metric:** Increment local counter `skyra_logging_drop_count` for observability.

---

## 9. Compatibility & Future Centralized Export

This JSONL contract is designed for seamless forward-compatibility with:
- Skyra LogHub Parquet Compactor (ADR-011)
- Vector / Fluent Bit / Promtail file-tailing agents
- Cloud object storage sync (`aws s3 sync`, `azcopy`, Google Cloud Storage transfer)
- Ad-hoc DuckDB direct queries: `SELECT * FROM read_ndjson('/var/log/skyra/**/*.jsonl')`
