## Provider and callback recommendation — proposal only

Recommend **Keycloak as the first candidate**, provided the team accepts responsibility for hosting, upgrades, availability and key management. This is an architecture-fit recommendation, not a selected or provisioned provider. Its documented authorization/token endpoint paths match the BFF's existing layout; it also exposes discovery and public realm keys. See [Keycloak OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers). If operating an identity service is undesirable, evaluate a managed provider such as Auth0 as a regular web application; its [server web-app guide](https://auth0.com/docs/quickstart/webapp/express/index) describes server-side client credentials and callback registration. A managed alternative would also require removing the BFF's Keycloak-specific endpoint assumptions.

For either option, register the **BFF as a confidential server-side client** with Authorization Code + S256 PKCE. A client ID is public metadata; this does not mean the client should be configured as a public SPA. Client credentials and token exchange stay in BFF. Keep LogHub organization membership/OrgOwner assignment authoritative in PostgreSQL rather than trusting arbitrary IdP role/email claims. [Keycloak client settings](https://www.keycloak.org/docs/latest/server_admin/index.html#_oidc_clients) distinguish server-side client authentication from public browser clients.

Use the public browser-facing BFF URL, not the Admin Service port, IdP URL or an Angular route. For deployed environments, route `/bff` on the console origin to BFF so the callback sets its cookie on the same public console host. For local testing use 127.0.0.1 consistently for both console and BFF, rather than mixing localhost and 127.0.0.1. Register exact URIs without wildcard paths and use separate client registrations/secrets per environment. The client identifier may follow an environment-specific naming convention such as `skyra-console-bff-dev`; this is a proposed label, not an existing registration. Do not register or use an invented issuer/hostname.

For an eventual Keycloak selection, derive the exact realm issuer and endpoints from that approved server's discovery metadata. Recommend an explicitly allowed asymmetric signing algorithm such as RS256 with maintained JOSE verification, configured-issuer discovery/JWKS, kid selection, bounded caching/refresh and rotation/error tests. The current HS256-only code is **not ready for that proposed asymmetric configuration**. Do not weaken provider signing to preserve the current verifier. No discovery/JWKS code or real-provider provisioning is introduced solely by this recommendation; implement and verify the selected contract before Approval C, while existing synthetic HS256 tests continue to validate current fail-closed behavior.

## Current implementation and targeted corrections

Source: `apps/console-bff/src/modules/auth/application/oidc.service.ts` and `src/config/bff-config.service.ts`.

The existing verifier accepts only HS256 with its configured symmetric client secret; rejects none, RS256, ES256 and forged signatures; checks exact issuer, expected audience, authorized party for multiple audiences, nonce, finite numeric expiry with ten-second skew, and nonempty string subject. It does not fetch JWKS, select kid, cache keys or handle asymmetric rotation. Token-supplied jku/kid do not select a trusted key. Missing/rotated asymmetric keys always fail because their algorithms are unsupported; this is not a JWKS implementation or a successful key-rotation test.

001C adds numeric/finite nbf enforcement with the same skew; exact ten-minute state expiry at callback time rather than reliance on periodic cleanup; five-second token-exchange abort and redirect refusal; and sanitized network/HTTP failures that omit upstream response bodies and exception details. Existing S256 PKCE, random state/nonce, one-use state deletion, audience and signature requirements remain. Authorization/token URLs still use the fixed configured issuer plus Keycloak-style `/protocol/openid-connect/auth` and `/token`; discovery endpoint selection remains unimplemented. Malformed JSON/token responses cannot create a session, but a complete provider-adapter error taxonomy remains outside this missing-provider milestone.

Authoritative membership outside NODE_ENV=test now fails startup if mock OIDC is enabled, explicit issuer/client/callback/Admin endpoint/origin allowlist is absent, or OIDC/internal/session/CSRF secrets are absent or shorter than 32 characters. It validates HTTPS issuer without credentials/query/fragment, endpoint transport (HTTP only for loopback in nonproduction), cookie SameSite lax/strict, and finite positive session lifetimes. Production cookies remain Secure. Setting NODE_ENV=test is reserved for the isolated harness and must never appear in protected configuration. No environment file or activation flag was changed. Ordinary development previews remain available with authoritative mode off.

## Sessions, authorization and CSRF

Successful validated callback resolves authoritative persisted memberships before creating a session. Cookies contain a random 256-bit opaque session ID, HttpOnly, root path, Secure in production and SameSite lax by default (strict configurable). Source architecture's blanket Strict description is not the current default; Approval C must select lax/strict deliberately with the actual IdP callback flow.

Tokens stay server-side; safe session DTOs and organization projections do not expose them. SessionAuthGuard enforces absolute and idle timeouts and rejects missing/revoked sessions. CSRF requires session-bound random token with constant-time comparison plus allowed Origin/Referer on mutations. Logout deletes server state and clears configured/legacy cookies. Organization calls additionally resolve current active DB identity/membership and tenant capability on every request; a stale browser role list cannot authorize a revoked account. The internal assertion is signed with an explicitly configured separate secret, scoped and valid for at most 60 seconds. Missing flags, credentials or service availability deny organization forwarding.

Session and pending-state storage are process-local memory. Approval C must use one BFF instance (with ordinary restart forcing fresh login) or commission a shared-store change and its tests before scaling. Automatic IdP refresh/revocation synchronization and asymmetric JWKS rotation are not established. A managed HS key change requires coordinated provider/BFF change and session invalidation; it is not automatic rotation. Never carry isolated mock sessions into activation; restart BFF and establish fresh real sessions.
